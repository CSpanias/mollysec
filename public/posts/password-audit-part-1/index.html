Password Audits Part 1: NTDS Extraction

Mar 13, 2026 · 16 min read  ·
Share on:

Introduction

What is a Password Audit?

A password audit is a systematic evaluation of an organization’s password security posture. In the context of Active Directory (AD) environments, this involves extracting credential hashes from the domain database, attempting to crack them using various techniques, and analyzing the results to identify weaknesses in password policies and user behavior.

Unlike unauthorized credential theft, password audits are conducted with explicit client authorization as part of security assessments, penetration tests, or compliance reviews. The goal is not exploitation, but rather providing actionable intelligence that helps organizations strengthen their authentication controls.

What are the Goals of a Password Audit?

A comprehensive password audit serves multiple security objectives:

  • Identify Weak Passwords: Discover accounts using common passwords, dictionary words, or easily guessable patterns that could be compromised through brute-force or password spraying attacks.
  • Assess Policy Effectiveness: Evaluate whether existing password policies (length, complexity, expiration) translate into actual password strength across the user population.
  • Detect Credential Reuse: Identify users who reuse passwords across multiple accounts or services, creating a single point of failure.
  • Highlight High-Value Targets: Focus on privileged accounts (e.g .Domain Admins) that use weak credentials, representing critical security risks.
  • Measure Security Posture: Provide quantitative metrics (percentage of cracked hashes, time-to-crack distributions) that demonstrate organizational password hygiene.
  • Drive Remediation: Deliver specific, actionable recommendations: from forced password resets to policy adjustments to user security awareness training.

How Passwords are Stored in Active Directory

AD does not store passwords in plaintext. Instead, it stores cryptographic hashes: one-way mathematical transformations of the password that cannot be reversed to recover the original plaintext.

When a user authenticates, Windows hashes the provided password and compares it to the stored hash. If they match, authentication succeeds. This design means that even with access to the hash database, attackers (or auditors) must use computational methods to recover passwords, i.e., the “cracking” process.

AD primarily uses NTLM hashes (also called NT hashes), which are MD4 hashes of the Unicode password. Legacy systems may also store LM hashes, an older, weaker format that is rarely enabled on modern networks.

These hashes are stored in NTDS.dit (NT Directory Services Directory Information Tree), AD’s core database. Located on every Domain Controller (DC), NTDS.dit contains:

  • All domain user accounts and their password hashes (NTLM and, if available, LM hashes)
  • Group memberships and organizational unitsS
  • ervice Principal Names (SPNs) for additional attack surface analysis
  • Historical password data (depending on domain password policy settings)
  • Trust relationships between domains and forests

For password auditing, NTDS.dit represents the complete credential dataset we need to analyze organizational password hygiene, identify weak authentication practices, and provide comprehensive security recommendations.

However, NTDS.dit alone is encrypted and unusable. The hashes within are encrypted using keys derived from the Boot Key (SYSKEY), which is stored in the SYSTEM registry hive. This encryption protects the database at rest, but once we extract both NTDS.dit and the SYSTEM hive, we can decrypt and extract the hashes for analysis.

Think of it as a two-key system: NTDS.dit is the locked vault, and the SYSTEM hive provides the master key.

What We Usually Get During a Password Audit

In most password audit engagements, the client provides us with Domain Administrator (DA) credentials or equivalent privileged access. Remember that the goal here is to assess password strength across the entire domain, not to test perimeter defenses or privilege escalation paths. With DA access, we can:

  1. Remotely connect to a DC
  2. Extract the NTDS.dit database and SYSTEM registry hive
  3. Transfer files back to our analysis environment (typically a Kali Linux host)
  4. Decrypt and parse the database to obtain all user password hashes
  5. Begin the cracking and analysis phase

NTDS Extraction

With pre-authorized DA credentials, our extraction strategy emphasizes speed and efficiency. We aim to minimize engagement time while ensuring complete data capture. By selecting reliable methods that work across various AD configurations, we maintain data integrity for extracted hashes, ensuring they are ready for downstream cracking. Additionally, we prioritize tools that integrate smoothly with our existing password auditing pipeline.

Since we typically operate from a Kali host, the focus will be on remote extraction.

Extracting the files locally by jumping from Kali into a Windows host via RDP or WinRM access can have both pros and cons. It enables direct file system access, allowing us to bypass network restrictions on SMB or RPC, and local execution can improve performance, especially for large files, while providing full control and insight into local logs and processes for further analysis. However, it can also add complexity to the workflow, potentially increasing engagement time, and resource limitations on the target host may hinder execution speed. Additionally, security policies can lead to misconfigurations, and the required tools must be present and properly configured on the target host.

Impacket’s secretsdump

Source code: secretsdump.py

Impacket’s secretsdump performs a DCSync operation, leveraging the Directory Replication Service Remote Protocol (MS-DRSR) to request credential material directly from the DC. This mimics legitimate DC replication traffic, extracting password hashes without touching the NTDS.dit file on disk.

The basic command for NTLM hash extraction is:

secretsdump.py 'DOMAIN/username:password@<DC_IP>' -just-dc-ntlm

For more comprehensive extraction that captures additional credential material:

secretsdump.py 'DOMAIN/username:password@<DC_IP>' -outputfile extracted_creds

Analyse secretsdump.py script

Secretsdump has earned its position as an industry standard through extensive documentation, rigorous testing, and widespread trust within the offensive security community. The DCSync approach leverages AD’s own replication mechanisms, requesting credentials as if we were another DC legitimate synchronization.

When we invoke secretsdump, it establishes an authenticated connection to the target DC and initiates what appears to be a standard replication request using the DRSGetNCChanges function. The DC, believing it’s servicing a replication request from another DC, responds by transmitting the requested directory objects including password hashes. The data is returned in a linked-list structure that must be parsed and converted into a readable format. Secretsdump’s internal modules handle this conversion, extracting NTLM hashes from the replication stream. The entire operation occurs over the network using RPC interfaces (DRSUAPI - UUID: e3514235-4b06-11d1-ab04-00c04fc2dcd2), with no direct file system access required on the target DC.

This approach avoids disk I/O entirely on the target system. All credential data is transmitted over the network, making it one of the fastest extraction methods available. We need an account with Replicating Directory Changes and Replicating Directory Changes All permissions; typically DA credentials or accounts specifically delegated these rights.

When using the -outputfile flag, secretsdump generates multiple files containing different credential types. The .ntds file contains NTLM hashes for all domain accounts, while .ntds.cleartext captures any cleartext passwords stored in AD attributes. The .ntds.kerberos file includes Kerberos keys (AES256, AES128, and DES), and additional files capture the local SAM database hashes from the DC (.sam) as well as LSA secrets, cached credentials, and machine account passwords (.secrets).

The granular control offered through command-line flags like -just-dc-ntlm, -just-dc-user, and -history allows us to tailor extraction to specific engagement requirements. If we only need NTLM hashes for password cracking, we can skip the additional credential material to reduce extraction time.

Secretsdump uses a multi-protocol approach that requires both SMB and RPC access. The tool first establishes an SMB connection (TCP 445) for authentication and initial enumeration, then performs the actual DCSync operation using the DRSUAPI protocol over RPC (TCP 135 plus dynamic high ports in the range 49152-65535).This SMB-first behavior has practical implications for network-restricted environments.

When using Kerberos authentication, secretsdump requires the CIFS/domaincontroller SPN to establish the initial SMB session. If we’re operating in an environment where SMB is restricted or blocked but LDAP remains available, secretsdump may fail where pure LDAP-based methods succeed.This is the key distinction between secretsdump and Mimikatz’s DCSync implementation.

Mimikatz uses LDAP for its initial authentication and connection establishment, then proceeds to DRSUAPI for the credential extraction. This LDAP-based approach allows Mimikatz to function in environments where SMB access is restricted, while secretsdump’s SMB dependency can become a limiting factor. For most password audit engagements, this distinction is just a good-to-know detail as both SMB and LDAP are typically accessible to the DA. However, understanding the protocol requirements helps us troubleshoot connectivity issues and select alternative methods when network restrictions create obstacles.The output files benefit from organization if we’re extracting from multiple DCs, though this is easily managed with a consistent directory structure.

NetExec’s Methods

NetExec provides four distinct methods for extracting AD credentials from the NTDS.dit database on DCs. Each method employs different technical approaches with varying tradeoffs in terms of speed, reliability, and operational requirements.

Method 1: DRSUAPI - Remote Replication

NetExec’s --ntds option, implementend in smb.py, is a wrapper around Impacket’s secretsdump DCSync functionality. The operation is identical to running secretsdump.py -just-dc directly: it performs DCSync via the MS-DRSR protocol.

Method 2: Volume Shadow Copy Service

The --ntds vss method takes a fundamentally different approach by creating a Volume Shadow Copy snapshot of the system volume on the target DC. This snapshot provides a point-in-time copy of the file system that can be accessed while the live NTDS.dit file remains locked by the AD database engine.

nxc smb 192.168.1.100 -u da-mollysec -p 'Passw0rd123!' --ntds vss

While slower than DRSUAPI due to the file copy operations, this method can be useful when DRSUAPI access is restricted. It requires local administrator privileges on the DC but does not require specific AD replication permissions.

Method 3: NTDSUTIL Module - Living Off the Land

The ntdsutil module, implementend in ntdsutil.py,leverages Microsoft’s legitimate ntdsutil.exe administrative tool. This method uses the Install From Media (IFM) functionality, which was designed to allow administrators to create installation media for new DCs without requiring network-based replication.

nxc smb 192.168.1.100 -u da-mollysec -p 'Passw0rd123!' -M ntdsutil

The --enabled flag filters output to display only accounts that are currently enabled in AD, reducing noise from disabled accounts of former employees or decommissioned services. Method 4: NTDS-DUMP-RAW Module - Raw Disk Access

The ntds-dump-raw module, implementend in ntds-dump-raw.py, takes a fundamentally different approach by bypassing the Windows filesystem layer entirely. It reads raw disk sectors directly from \\.\PhysicalDrive0, allowing extraction of files that are actively locked by the operating system, such as NTDS.dit, which is held open exclusively by the AD database engine (ntds.exe).

The module reads the first 1024 bytes of the physical disk to identify the partition scheme (MBR or GPT) and locate the NTFS system partition:

It then reads the NTFS boot sector to extract filesystem metadata, i.e., bytes per sector, sectors per cluster, and the Master File Table (MFT) starting location:

The MFT contains a record for every file and directory on the volume. The module extracts the entire MFT (typically ~99MB on a DC) and parses it to locate ntds.dit, SYSTEM, and SECURITY. For each file, it:

  1. Searches MFT records by examining the $FILE_NAME attribute
  2. Reconstructs the full path to verify it’s extracting the correct file (e.g., C:\Windows\NTDS\ntds.dit)
  3. Decodes NTFS data runs to determine which physical disk clusters contain the file content
  4. Reads file data directly from raw disk clusters, then gzip-compresses and base64-encodes it before transfer

With files successfully transferred, the module extracts the Boot Key from the SYSTEM registry hive and instantiates Impacket’s NTDSHashes class with isRemote=False to parse the ESE database locally:

This method requires local administrator privileges and remote code execution capability. While it bypasses filesystem locks and does not require VSS, it generates significant network traffic during MFT and file extraction. The operation leaves minimal artifacts on the DC beyond command execution logs, as no shadow copies or temporary files are created on the target system.

Native Windows Approach: ntdsutil.exe

Ntdsutil is Microsoft’s native utility for NTDS database management, and its “Install From Media” (IFM) creation feature produces a complete, offline copy of NTDS.dit along with the necessary registry hives. This functionality was originally designed for promoting new domain controllers without network replication, but it serves our password audit purposes perfectly.

The IFM creation command is remarkably simple:

ntdsutil "activate instance ntds" "ifm" "create full C:\\temp\\ntds_dump" quit quit

Alternatively, we can use VSS snapshots for more granular control:

ntdsutil snapshot "activate instance ntds" create quit quit
ntdsutil snapshot "mount {GUID}" quit quit
copy <mounted_snapshot_path>\\Windows\\NTDS\\ntds.dit C:\\temp\\
copy <mounted_snapshot_path>\\Windows\\System32\\config\\SYSTEM C:\\temp\\

The native Windows approach offers significant advantages when we already have interactive access to a domain controller through RDP or WinRM. As a built-in Windows utility, ntdsutil requires no third-party software installation. The direct filesystem access eliminates network overhead, making this typically the fastest extraction method available. The tool produces clean, ready-to-transfer files in a single directory and leverages Windows’ native shadow copy infrastructure for reliable VSS handling.

Ntdsutil does require execution directly on the domain controller, which means we need RDP, WinRM, or PSExec access. We also need to ensure sufficient disk space for the IFM set, which typically consumes several gigabytes depending on the Active Directory database size.

This method excels when we’re operating from a Windows jump host within the client environment rather than our Kali attack platform. If we’ve already established an RDP session to perform other domain controller analysis, ntdsutil becomes the most efficient option available.

After extraction, we need to transfer the large files off the DC back to our analysis environment. We should also clean up the IFM directory to avoid leaving unnecessary artifacts, though from a pure password audit perspective this is more about professional hygiene than operational security.

DCSync via Mimikatz

Mimikatz’s DCSync module performs the same Directory Replication Service operations as secretsdump, but with a pure LDAP-based approach. Unlike Impacket’s SMB-first methodology, Mimikatz doesn’t require CIFS SPNs or SMB access, which can be advantageous in certain network configurations.

The command for complete credential extraction is:

lsadump::dcsync /domain:targetdomain.com /all /csv

For targeting specific high-value accounts:

lsadump::dcsync /domain:targetdomain.com /user:Administrator

The LDAP-only operation works well in environments where SMB faces additional restrictions. Mimikatz displays hashes immediately in real-time output without creating intermediate files, which can be useful for quick verification. The selective extraction capability allows us to target specific accounts when we need rapid confirmation of particular credentials before committing to a full NTDS extraction.

However, Mimikatz requires execution on a Windows host, typically accessed via RDP or WinRM. The output requires parsing if we need standardized file formats compatible with our cracking tools, as the default console output isn’t optimized for direct ingestion into Hashcat or John the Ripper.

DCSync via Mimikatz is particularly useful when we’re already operating from a Windows host and need quick verification of specific account credentials. For comprehensive password auditing requiring all domain hashes, secretsdump or NetExec typically provide better workflow integration.

Conclusion

This first installment has established the foundational components of Active Directory password auditing: understanding how credentials are stored, why NTDS.dit extraction requires both the database and SYSTEM hive, and the various methods available for obtaining this critical data.

We’ve examined five distinct extraction approaches, each with specific technical implementations and operational tradeoffs:

  • Impacket’s secretsdump remains the industry standard for remote DCSync operations, offering reliable DRSUAPI-based extraction with minimal disk activity on the target DC. Its SMB dependency is rarely a limitation in standard password audit engagements.
  • NetExec’s four methods provide tactical flexibility: the default DRSUAPI wrapper for standard operations, VSS when replication permissions are unavailable, ntdsutil for living-off-the-land approaches, and raw disk access when filesystem-level restrictions apply.
  • Native ntdsutil.exe excels when we already have interactive access to a domain controller, delivering the fastest extraction through direct filesystem access without network overhead.
  • Mimikatz DCSync offers LDAP-based replication that bypasses SMB requirements, useful for quick verification of specific accounts or environments with restrictive network policies.

With DA credentials and network access to a domain controller, any of these methods will successfully extract the complete credential dataset. The choice between them depends on operational context: whether we’re working remotely from Kali or locally from a Windows host, whether we need all hashes or targeted extraction, and whether specific network protocols face restrictions.

We’ll parse the raw output into structured formats, separate user accounts from computer accounts, identify privileged credentials, and prepare our hash lists for analysis.
